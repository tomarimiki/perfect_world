# 実装前に決めておくこと（Claude Code に書かせる前のチェックリスト）

> `design.md` は「何を作るか」を書いた設計書。
> このファイルは「design.md に**書かれていないせいで、AI が勝手に決めてしまう**こと」を潰すためのもの。
> ここが埋まっていないままコーディングを始めると、毎回違う実装が出てきて手戻りする。

**`design.md` は編集しない。** 決定した内容はこのファイルに書き、実装時は両方を渡す。

## 使い方

- 各項目に **選択肢** と **推奨** を書いてある
- 推奨でよければ `→ 決定:` の行に「推奨」と書くだけでいい
- 全部埋めなくてもよい。**A章とC章だけは着手前に埋める**（ここが空だと必ず手戻りする）
- B章（design.md の矛盾）は、放置すると「バグなのか仕様なのか」が判別不能になる。優先度高

# A. 仕様の穴（design.md に書かれていない）

## A-1. コードを置く場所

`design.md` は作業フォルダを `solar-lab` と書いているが、このリポジトリ名は `Solar-system-lawbreaker-design`。

| 選択肢 | 内容 |
|---|---|
| ア | このリポジトリのルートに直接 `index.html` などを置く |
| イ | このリポジトリに `app/` を作ってその中に置く |
| ウ | 実装は別リポジトリにして、ここは設計書専用にする |

**推奨：イ**。設計書とコードが混ざらず、`app/` をそのまま GitHub Pages の公開ディレクトリにできる。

→ 決定: イ（app/ 配下に移動。実施済み）

## A-2. 画面が壊れたときの扱い（最重要）

法則を壊すと、惑星は**必ず**「太陽に落ちる」か「画面外へ飛ぶ」。その後どうするかが決まっていない。

決めること：

- 画面外に出た天体をどう扱うか（そのまま計算し続ける／画面端に矢印を出す／自動ズームアウト）
- 太陽に接近して `r` が極小になったとき（加速度が爆発してトレイルが暴れる）
- 座標が `NaN` / `Infinity` になったときの復帰方法

| 選択肢 | 内容 |
|---|---|
| ア | 何もしない。飛んでいったらリセットボタンを押してもらう |
| イ | `r < 0.01 AU` で「落下」判定、その天体を停止して灰色表示にする |
| ウ | 自動ズーム（全天体が入るようスケールを毎フレーム調整） |

**推奨：ア＋NaN検出だけ実装**。`NaN` を検出したら自動で一時停止し、「計算が破綻しました／リセットしてください」と画面に出す。
自動ズームは「軌道が広がった」という体験そのものを消してしまうので初期版では入れない。

→ 決定: ア＋NaN検出（推奨採用）

## A-3. ズームとパン

`SCALE = 220` 固定だと、`sunMass` を下げた瞬間に全惑星が画面外へ出る。

| 選択肢 | 内容 |
|---|---|
| ア | ズームスライダー（0.2〜3倍）を1本追加。パンなし |
| イ | マウスホイールでズーム、ドラッグでパン |
| ウ | 固定のまま（Day 8 以降に回す） |

**推奨：ア**。スライダー1本なら他のUIと統一が取れるし、実装は `SCALE` を変数にするだけで済む。

→ 決定: ア（ズームスライダー1本、パンなし）

## A-4. 「時間の流れ」を dt で変えるか、ステップ数で変えるか

`design.md` は速度調整用のつまみが2つある：`law.dt`（7章のスライダー）と `STEPS_PER_FRAME = 20`（9-1）。
**dt を大きくすると計算精度が落ちて軌道が崩れる**ので、この2つを混ぜると「法則を壊したせい」なのか「dt を上げたせい」なのか区別できなくなる。

| 選択肢 | 内容 |
|---|---|
| ア | `dt` は 1/2000 固定（符号だけ反転可）。速度は `STEPS_PER_FRAME` で変える |
| イ | `dt` スライダーをそのまま出す |
| ウ | 両方出すが、`dt` を既定から動かしたら画面に「精度低下中」と表示する |

**推奨：ア**。「時間の流れ」スライダーの実体を `STEPS_PER_FRAME`（1〜100）にして、負の値のときだけ `dt` の符号を反転する。
これなら**逆再生は正確なまま、速度だけ変わる**。

→ 決定: ア（dt は 1/2000 固定。速度は STEPS_PER_FRAME で変える。負の値のときだけ dt の符号を反転）

## A-5. 一時停止・リセット・コマ送り

決めること：

- 一時停止ボタンは要るか（推奨：要る。スペースキーでも切り替え）
- リセットしたとき、**スライダーの値も既定に戻すか**（推奨：戻さない。法則は維持して配置だけ戻す）
- リセットでトレイルは消すか（推奨：消す）
- リセットで経過年数は 0 に戻すか（推奨：戻す）
- コマ送り（1ステップだけ進める）は要るか（推奨：初期版では不要）

→ 決定: すべて推奨採用（一時停止ボタンあり・スペースキー対応、リセットでスライダー値は維持し配置のみ戻す、トレイルは消す、経過年数は0に戻す、コマ送りは初期版では不要）

## A-6. スライダーを動かした瞬間の挙動

これが**このアプリの体験の核心**なのに、design.md に書かれていない。

決めること：

- スライダーを動かしたとき、トレイルを消すか残すか
  - **推奨：残す。** 「元は楕円だったのに、ここから花びらになった」が1枚の絵で見えるのが一番劇的
- 変更した瞬間、エネルギーグラフに縦線マーカーを引くか
  - **推奨：引く。** 「壊した瞬間に線が折れた」の因果が見える
- 変更を「その瞬間から」効かせるか、リセットするまで効かせないか
  - **推奨：その瞬間から**（design.md 9-2 の方針どおり）

→ 決定: すべて推奨採用（トレイルは残す、変更した瞬間にエネルギーグラフへ縦線マーカー、変更はその瞬間から効かせる）

## A-8. プリセットを押したときの、書かれていない項目の扱い

# B. design.md の中で、実装すると矛盾する箇所

## B-1. トレイルの上限が2つある

- 8-3 と 9-1 のコード：`if (b.trail.length > 3000)`
- 12章の対処表：「trailが長すぎる → 上限を1000程度に下げる」

**推奨：1500 に統一**。長すぎると花びら模様が塗り潰れて、短すぎると軌道が閉じていない証拠が消える。

→ 決定: ___1500_____

## B-2. 重力定数 G が2箇所にある（実害あり）

- `data.js`：`export const G = 4 * Math.PI * Math.PI;` → `createBodies()` の初期速度計算に使われる
- `law.G`：スライダーで変更できる

このため、**G のスライダーを動かしてからリセットを押すと、初期速度だけ元の G のまま**になる。「G を変えた宇宙での正しい円軌道」にはならない。

| 選択肢 | 内容 |
|---|---|
| ア | `createBodies(law)` に変更し、現在の `law.G` で初期速度を計算する |
| イ | 現状のまま（リセットは常に「現実の初期条件」に戻る、と割り切る） |

**推奨：イ＋明記**。リセットの意味を「現実の太陽系の初期配置に戻す」と定義したほうが体験として一貫する。ただし**この挙動を意図的なものとしてコードにコメントで残す**（残さないと後で必ずバグ報告される）。

→ 決定: イ（現状のまま。リセットは常に「現実の初期条件」に戻る、と割り切る。この挙動を意図的なものとしてコードにコメントで残す）

## B-3. 太陽の扱いが非対称

6-4 のコードでは：

- `law.sunMass` は「**相手が**太陽のとき」だけ掛かる（`const mB = (j === 0) ? B.m * law.sunMass : B.m;`）
- 太陽自身の慣性質量は `1.0` のまま
- 重力波減衰 `gw` は `i > 0`（太陽には効かない）
- 宇宙定数 `lambda` は太陽にも効く（太陽は原点付近なのでほぼ0だが、ずれると効く）

つまり作用・反作用が崩れていて、**系全体の運動量が保存しない**。物理的には「壊れている」が、このアプリは壊すのが目的なので問題とは限らない。

決めること：

| 選択肢 | 内容 |
|---|---|
| ア | 太陽を完全に固定する（`bodies[0]` は動かさない）。一番分かりやすく、絵も安定する |
| イ | 現状どおり太陽も動かす（重心のドリフトは受け入れる） |

**推奨：ア**。太陽固定なら「軌道が壊れた」ことだけが画面に出る。イだと画面全体がじわじわ流れて、原因の切り分けが難しくなる。
（Day 8 で「太陽も動かすモード」を足せばよい）

→ 決定: ___ア_____

## B-4. エネルギーの式が、次元を変えると合わなくなる

`totalEnergy()` のポテンシャルは `-G·m1·m2/r`。これは**3次元（逆二乗）専用の式**。
`dimension` を 3.4 にすると、力の式とエネルギーの式が別の法則を指すことになる。

このとき「エネルギーが保存しない」と表示されても、それが**法則を壊した結果なのか、式が対応していないだけなのか判別できない**。design.md 11章のテスト2が意味を失う。

| 選択肢 | 内容 |
|---|---|
| ア | `dimension ≠ 3` のときはエネルギー表示を「—（定義されません）」にする |
| イ | 一般次元のポテンシャル `-G·m1·m2·r^(2-exponent)/(exponent-1)` を実装する |
| ウ | 気にせず現状の式で出す |

**推奨：ア**。正直に「この法則ではエネルギーが定義できない」と出すほうが、体験としても正しい。実装も一番軽い。

→ 決定: ア（dimension ≠ 3 のときはエネルギー表示を「—（定義されません）」にする）

## B-5. 相対論補正が惑星どうしにも掛かる

`if (law.gr > 0)` のブロックは `j` が太陽かどうかを見ていない。惑星間の弱い引力にも GR 補正が乗る。
また `h` は「自分（A）の原点まわりの角運動量」なので、相手が惑星のときは物理的な意味を持たない。

**推奨：太陽（`j === 0`）のときだけ適用する**。1行の条件追加で済む。水星の近日点移動という主目的には影響しない。
